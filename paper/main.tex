\begin{abstract}
Custom GPU kernels for image preprocessing and detector postprocessing are often proposed to cut
latency in single-stream (batch-1) vision pipelines. We implement two such kernels in Triton, a
fused \texttt{uint8} HWC$\rightarrow$normalized CHW preprocessor and a single-pass YOLO candidate
filter with in-kernel stream compaction, and measure them in isolation and inside two complete
pipelines (a 256$\times$256 convolutional autoencoder and pretrained YOLOv8n at 640$\times$640) on
an RTX~4050 Laptop GPU. We separate \emph{device time} (GPU execution with launch overhead hidden)
from \emph{host latency} (what the application waits for). In isolation, the preprocessing kernel
is \res{pre/speedup_vs_eager/min}--\res{pre/speedup_vs_eager/max}$\times$ faster than PyTorch eager
on the GPU and \res{pre/speedup_vs_compiled/min}--\res{pre/speedup_vs_compiled/max}$\times$ as fast as
TorchInductor, but for small frames a single call's host latency is dominated by dispatch. The fused filter cuts
host latency \res{filter/640/warm/host_speedup_vs_eager}$\times$ relative to eager
(\res{filter/640/eager/warm/host} $\rightarrow$ \res{filter/640/triton/warm/host}\,\textmu s), yet its kernel accounts for only
\res{filter/640/triton_kernel_only/warm/dev}\,\textmu s of that. End to end, swapping in either
kernel changes pipeline latency by less than run-to-run variation, while capturing the static part
of each pipeline in a CUDA graph reduces latency by \res{pipe/anomaly/pre=triton,model=eager,cuda-graph/gain}\%
(anomaly) and \res{pipe/detection/pre=triton,model=eager,filter=triton,cuda-graph/gain}\% (detection).
At batch 1 on this hardware, launch overhead, not memory traffic, decides the outcome. We also
document three benchmarking pitfalls, each of which changed a conclusion during this study, and a
compiler bug that silently corrupts compiled YOLOv8n outputs.
\end{abstract}

\section{Introduction}
Inspection and detection systems often process one camera frame at a time under a latency budget.
Around the neural network, such pipelines run non-neural steps: layout conversion and
normalization before the model, candidate filtering and non-maximum suppression (NMS) after it.
Written as framework operator chains~\cite{paszke2019pytorch}, these steps launch several small
kernels and materialize intermediate tensors. Fusing them into custom kernels~\cite{tillet2019triton}
is a common recommendation. This paper asks a narrow question: \emph{on a batch-1 pipeline, how much
latency does such fusion remove, compared with what the GPU compiler and CUDA graphs already provide?}

\noindent\textbf{Contributions.}
(1)~Two Triton kernels: a fused preprocessor that folds normalization into one FMA per element,
and a single-pass candidate filter that reduces 80 class scores, thresholds, decodes boxes and
compacts survivors on the GPU with one host synchronization.
(2)~A measurement protocol that reports GPU device time and host latency separately, with cold
and warm caches and interleaved repeated blocks.
(3)~Results against PyTorch eager, TorchInductor~\cite{ansel2024pytorch} and manual CUDA-graph
capture~\cite{nvidia2025cudaguide}, from isolated kernels up to full pipelines, with Nsight
Compute~\cite{nvidia2025nsightcompute} counters.
(4)~Benchmarking pitfalls and a correctness bug: a hidden synchronization inside a timed region,
which in an earlier version of this work produced a spurious $5\times$ slowdown; cache flushes that
hide launch overhead or charge dirty-line write-back to the measured kernel; and a TorchDynamo
mis-trace that silently corrupts \texttt{torch.compile}d YOLOv8n outputs.
All code, raw results and the generator of every number in this paper are public.\footnote{\url{https://github.com/sengarutk/cuda-kernels-edge-vision}}

\section{Background}
Operator fusion is a central technique of ML and image-processing compilers such as
Halide~\cite{ragankelley2013halide}, TVM~\cite{chen2018tvm} and TorchInductor~\cite{ansel2024pytorch},
and of hand-written kernels such as FlashAttention~\cite{dao2022flashattention}. It removes
intermediate global-memory traffic and kernel launches. Both savings are bounded by Amdahl's
law~\cite{amdahl1967validity}: they only matter if the fused stages make up a meaningful part of
end-to-end time. GPU memory behaviour (coalescing, sector use, caching) is analysed with
microbenchmarks and hardware counters~\cite{mei2017dissecting,nvidia2025nsightcompute}.
CUDA graphs~\cite{nvidia2025cudaguide} remove per-kernel launch cost by replaying a captured
sequence of kernels. Libraries such as DALI~\cite{nvidia2023dali} and TensorRT~\cite{nvidia2024tensorrt}
target the same pipeline stages in production.

\section{Kernels}
\noindent\textbf{Kernel 1: preprocessing.} The kernel computes
$y_{c,h,w} = x_{h,w,c}\cdot s_c + b_c$ with $s_c = 1/(255\sigma_c)$ and $b_c = -\mu_c/\sigma_c$ folded
on the host. A 1D grid assigns consecutive pixels to each program (block size autotuned). Each
pixel needs three byte loads at stride~3 and three coalesced plane stores. Compulsory DRAM traffic
is $15P$ bytes for $P$ pixels in FP32. The 5-kernel eager chain (\texttt{to}, \texttt{div},
\texttt{sub}, \texttt{div}, \texttt{contiguous}) moves up to $111P$ bytes when no intermediate stays
in cache. FP16 output is computed in FP32 and rounded once. A 2D-tiled variant performs the
same arithmetic on $16{\times}16$-pixel tiles, so each tile row touches only 48 contiguous input bytes.

\noindent\textbf{Kernel 2: candidate filter.} YOLOv8~\cite{jocher2023yolov8,redmon2016you}
produces a $[1, 84, N]$ tensor: 4 box values and 80 sigmoid class scores per candidate. One program
handles a block of candidates. A compile-time-unrolled loop over classes keeps the running max and
argmax in registers, with coalesced loads in this channels-first layout. Survivors (score
$\geq 0.25$) are decoded from $(c_x, c_y, w, h)$ to corners and compacted in the kernel: each program
reserves output slots with one atomic add and orders its survivors with a prefix sum (cf.\ the
decoupled scan of Merrill and Garland~\cite{merrill2016single}). The host reads the survivor count
once. The eager baseline follows the Ultralytics pre-filter: one reduction, one \texttt{nonzero}
(also a single synchronization), then argmax and box conversion on the survivors only.

\section{Methodology}
\noindent\textbf{Setup.} \res{env/gpu} (\res{env/compute_capability}, \res{env/sm_count} SMs,
\res{env/l2_cache_mb}\,MB L2, 192\,GB/s peak DRAM), driver \res{env/driver}, \res{env/os} under WSL2,
PyTorch \res{env/torch}, Triton \res{env/triton}, Nsight Compute \res{env/ncu}.

\noindent\textbf{Timing.} \emph{Device time} uses CUDA events, with the stream pre-filled by a
spin kernel that outlasts the host's enqueue time, so the GPU never waits for the CPU inside the
timed window. \emph{Host latency} is wall-clock time from the call to a completed
\texttt{synchronize}. For cold-L2 runs, a 64\,MB buffer (more than twice the L2) is \emph{read}
before every call, outside the timed window. Reading matters: a write-based flush leaves the L2
full of dirty lines, and their write-back is then charged to the measured kernel
(Section~\ref{sec:discussion}). Isolated kernels run 300 timed calls after 30 warm-up
calls. Pipelines run 10 interleaved blocks of 300 frames per configuration, in an order that
rotates per block; we report pooled percentiles and the spread of block medians.

\noindent\textbf{Workloads.} Preprocessing uses random frames from 256$\times$256 to
3840$\times$2160. The filter and the detection pipeline use real YOLOv8n outputs for the
Ultralytics \texttt{bus.jpg} scene (\res{filter/640/cands} candidates, \res{filter/640/kept} above
threshold, 5 detections after NMS at 640$\times$640). The anomaly autoencoder has seeded random
weights: we measure latency, not accuracy~\cite{bergmann2019mvtec}. Every kernel output is verified
against PyTorch before timing (max FP32 deviation \res{pre/max_err_fp32}).

\subsection{Preprocessing in isolation}
Table~\ref{tab:pre} and Figure~\ref{fig:pre} show device times with a cold L2. The fused kernel is
\res{pre/speedup_vs_eager/min}--\res{pre/speedup_vs_eager/max}$\times$ faster than the 5-kernel eager
chain. TorchInductor fuses the same chain automatically. Relative to it, the Triton kernel is
\res{pre/speedup_vs_compiled/min}--\res{pre/speedup_vs_compiled/max}$\times$ as fast in FP32 (above~1
means faster) and \res{pre/fp16_speedup_vs_compiled/min}--\res{pre/fp16_speedup_vs_compiled/max}$\times$
in FP16, so hand-written fusion still has a margin over the compiler on some shapes. That margin is
measured in microseconds, though. Dispatching any kernel from Python costs tens of microseconds, so
a single call's \emph{host latency} improves over eager by \res{pre/1920x1080/host_speedup_vs_eager}$\times$
at 1080p, where GPU work dominates, but only \res{pre/256x256/host_speedup_vs_eager}$\times$ at
256$\times$256. There the Triton call takes \res{pre/triton_fp32/256x256/host}\,\textmu s on the host for
\res{pre/triton_fp32/256x256/dev}\,\textmu s of GPU work.

\subsection{2D tiling}
With identical, synchronization-free dispatch, the 2D-tiled variant takes
\res{pre/twod_slowdown/min}--\res{pre/twod_slowdown/max}$\times$ the device time of the 1D kernel.
Nsight Compute (Table~\ref{tab:ncu}, Figure~\ref{fig:stalls}) attributes this to memory access, not
register pressure. At 1080p
both kernels reach full theoretical occupancy, but the 2D kernel's global-load sector efficiency is
\res{ncu/preprocess_triton_2d_1920x1080/main/ldeff}\% against \res{ncu/preprocess_triton_1920x1080/main/ldeff}\%,
and its dominant stall is \res{ncu/preprocess_triton_2d_1920x1080/main/stall}
(\res{ncu/preprocess_triton_2d_1920x1080/main/stallpct}\% of stalls), a queue for memory instructions.
The 1D kernel is dominated by \res{ncu/preprocess_triton_1920x1080/main/stall}
(\res{ncu/preprocess_triton_1920x1080/main/stallpct}\%), i.e.\ waiting on DRAM. Short 16-pixel rows
issue more, smaller memory requests. An earlier version of this study reported a $5\times$ slowdown
caused by register pressure. That came from the 2D dispatcher reading CUDA-tensor normalization
constants with \texttt{.tolist()}, a device synchronization inside the timed region that the 1D path
did not perform.

\section{Discussion}
\label{sec:discussion}
\noindent\textbf{Where fusion pays.} The fused kernels remove most of the GPU work of their stages; at
1080p the preprocessing kernel sustains \res{ncu/preprocess_triton_1920x1080/main/dram}\% of peak DRAM
throughput under Nsight Compute. But at batch 1 on this system, the GPU
time they save is microseconds, while each Python-level dispatch costs tens of microseconds and the
model launches hundreds of kernels. Removing launches (CUDA graphs, model compilation) therefore
dominates. A custom kernel is most useful where the compiler cannot reach it (data-dependent
compaction, as in Kernel~2) or inside a graph-captured or C++ runtime, where its smaller GPU time is
no longer hidden behind dispatch.

\noindent\textbf{Measurement pitfalls.} Three effects changed conclusions while this study was
being done. First, any synchronization inside a timed region (here an innocuous \texttt{.tolist()})
turns kernel timing into host-latency timing for one side of a comparison only. Second, a cache-flush
kernel placed before each timed call also hides launch overhead behind the flush, so ``isolated''
GPU times silently exclude dispatch. Third, the common write-based flush (\texttt{zero\_()}) leaves
the L2 full of dirty lines: the 1080p preprocessing kernel writes \res{ncu/preprocess_triton_1920x1080/main/wrmb}\,MB
to DRAM during its own execution under Nsight Compute, but under a write-based flush it must also
evict up to \res{env/l2_cache_mb}\,MB of unrelated dirty data, a cost comparable to the kernel's own
runtime. With that flush the 1D and 2D kernels measured equally fast at 1080p, although Nsight Compute
shows a clear gap. We now flush by reading, report both device time and host latency, verify outputs before timing,
and generate every published number from stored results. A fourth pitfall concerns correctness: PyTorch~\res{env/torch}'s TorchDynamo mis-traces the
\texttt{y.extend(m(y[-1]) for m in ...)} pattern in Ultralytics' \texttt{C2f}/\texttt{SPPF} blocks, so a
\texttt{torch.compile}d YOLOv8n returned wrong boxes without any error. We rewrite those methods
as explicit loops and test bit-exact agreement with eager.

\noindent\textbf{Limitations.} One laptop GPU under WSL2, whose clocks and scheduler add variance
(we report block spreads); batch~1 only; FP32 models with cuDNN's default TF32 convolutions; no
TensorRT or Jetson evaluation; latency only, no accuracy.

\section{Conclusion}
On an RTX~4050 Laptop GPU, fused Triton kernels for batch-1 preprocessing and YOLO candidate
filtering are much faster than PyTorch eager on the GPU, match or beat TorchInductor for
preprocessing (up to \res{pre/speedup_vs_compiled/max}$\times$), and cut the filter's host latency
\res{filter/640/warm/host_speedup_vs_eager}$\times$. Yet they do not measurably change end-to-end
latency, which is set by kernel-launch overhead: CUDA graphs reduce it by about half, while the
custom kernels' remaining effect stays within run-to-run variation. Pipeline
optimization at batch~1 should start by removing launches and synchronizations, and every speedup
claim should state which of device time or host latency it measures.
