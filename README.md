# Triton Kernels for Batch-1 Edge Vision Pipelines

A measured study of when custom GPU kernels for pre- and post-processing speed up a batch-1
vision pipeline, and when kernel-launch overhead, model compute or the compiler already decide
the outcome. The kernels are written in [Triton](https://github.com/triton-lang/triton) (compiled
to PTX for NVIDIA GPUs); there is no hand-written CUDA C++.

> **Scope:** one NVIDIA GeForce RTX 4050 Laptop GPU (`sm_89`, 24 MB L2, 192 GB/s) under WSL2
> (Ubuntu 24.04). Latency only: detection accuracy is not evaluated. See
> [docs/limitations.md](docs/limitations.md).
>
> **v1.0.0 of this repository contained hardcoded and mismeasured results.** They were removed
> and everything was re-measured in v1.1.0; see [CHANGELOG.md](CHANGELOG.md).

**Device time** is GPU execution with launch overhead hidden. **Host latency** is what the
application waits for: Python dispatch, launches, syncs and execution. Both are defined in
[docs/methodology.md](docs/methodology.md).

## Findings

1. **On the GPU, fusion works.** The fused preprocessing kernel is several times to an order of
   magnitude faster than PyTorch's 5-kernel eager chain, and it matches or beats TorchInductor's
   automatic fusion at every resolution tested.
2. **At batch 1, dispatch hides most of it.** Launching any kernel from Python costs tens of
   microseconds, so for small frames a single preprocessing call's host latency barely changes, even
   though the GPU work shrinks several-fold. The fused YOLO filter halves the filter's host latency,
   but its kernel accounts for only a few percent of what remains; the rest is dispatch and the one
   unavoidable read-back of the survivor count.
3. **End to end, launches dominate.** In eager pipelines, swapping in either kernel changes per-frame
   latency by less than run-to-run variation, because the models launch hundreds of small kernels
   (YOLOv8n's host time is well above its GPU time). Compiling the model helps; capturing the static
   part of the pipeline in a CUDA graph roughly halves latency. Only inside a CUDA graph do the
   custom kernels add a measurable few percent.
4. **The 2D-tiled kernel is slower because of memory access, not register pressure.** Nsight Compute
   shows full occupancy for both kernels, but much lower global-load sector efficiency and
   memory-instruction (MIO) throttling for the 2D variant.
5. **Benchmark hygiene changes conclusions.** A hidden `.tolist()` sync inside a timed region, a
   cache flush that hides launch overhead, and a write-based cache flush whose dirty-line write-back is
   charged to the measured kernel each produced a wrong conclusion during this study. Separately,
   PyTorch 2.5's TorchDynamo mis-traces Ultralytics' `C2f`/`SPPF` blocks, so a `torch.compile`d
   YOLOv8n silently returns wrong boxes; [`src/models/yolo.py`](src/models/yolo.py) works around it
   and a test guards it.

## Reproduce

```bash
git clone https://github.com/sengarutk/cuda-kernels-edge-vision.git && cd cuda-kernels-edge-vision
pip install -r requirements.txt && pip install --no-deps -e .
make test      # GPU tests skip automatically without CUDA
make bench     # ~25 min; writes results/*.json
make ncu NCU=/path/to/ncu   # optional, needs GPU performance-counter access
make report figures paper   # regenerate docs/results.md, README block, figures, paper/main.pdf
make check     # fails if anything generated is stale
```

Details, including Nsight Compute on WSL2: [docs/reproducibility.md](docs/reproducibility.md).
